01
STEP 01

Code to GitHub

done

The project was committed with git and published to a private GitHub repository (Act-On-Issues-new-version) using GitHub Desktop — no command line needed. GitHub is what Cloud Run reads from directly later, rebuilding automatically on every push.

02
STEP 02

Production database — MongoDB Atlas

done

A free-tier (M0) Atlas cluster was created on Google Cloud, region asia-south1. A dedicated database login (actonissuesindia_db_user, separate from the Atlas account itself) was created for the app to connect with, and Network Access was opened to 0.0.0.0/0 — Cloud Run doesn't hand out a fixed, listable IP address, so this couldn't be narrowed further.

Good to know

The connection string always needs a database name in it — .../actonissue?retryWrites=..., not just .../?retryWrites=.... Missing this caused a real bug later in Step 08.

STEP 03

partially working

Brevo (free tier, 300 emails/day) handles OTP codes and notifications: smtp-relay.brevo.com on port 587. Technically functioning, but see Step 10 — deliverability is currently broken for a specific, understood reason.

STEP 05

File storage — Google Cloud Storage

done

Uploaded issue photos live in a public-read bucket, actonissue-images, rather than on Cloud Run's own disk — Cloud Run keeps no permanent local drive. The app authenticates via a dedicated service identity (storage-uploader@actonissue-9009.iam.gserviceaccount.com), not a downloaded key file, by literally running as that identity.

The production settings checklist

done

Everything above collapses into named values ("environment variables") the app reads on startup. There's no .env file in production — that only exists for a personal computer, and is excluded from GitHub entirely. Every value below is typed directly into Cloud Run's own settings instead.

Where to find this screen

Cloud Run → your service → Edit & deploy new revision → Containers tab → Variables & Secrets. Pasting a whole multi-line NAME=value block into the first Name box auto-splits it into separate rows — how all 11 values got entered in one paste, three separate times, once per region in Step 08.

NameWhere it came fromHow to find/regenerate it
NODE_ENVFixedAlways production
SESSION_SECRETRandom string, generated onceNot looked up anywhere — must stay identical across deployments, or every signed-in user gets logged out at once
COOKIE_SECUREFixedAlways true — without it, cookies aren't marked secure even over HTTPS
MONGO_URIBuilt from Atlas connection detailsAtlas → Database → Connect → Drivers gives the template; password from Database Access → Edit Password; the /actonissue database name has to be typed in by hand

The gotcha worth remembering

A brand-new Cloud Run service starts with zero environment variables, even one running identical code in a different region. Nothing carries over automatically. This block was re-pasted from scratch all three times a new service was created in Step 08.

08
STEP 08

The domain saga

resolved

The longest chapter in this whole project. The domain that ended up in use is actonissues.blog (GoDaddy), not the original actonissues.com.

08a · asia-south1 can't do domain mapping

Domain mappings are not available in the region of the selected service.

A real, permanent limitation of that specific Cloud Run feature — not every region supports it.

08b · A quota wall

Project failed to initialize in this region due to quota exceeded.

Every Google Cloud project caps how many different regions it may use Cloud Run in — this project's cap (3) was already spent. A manual increase was flatly declined:

Based on your service usage history, you are not eligible for a quota increase at this time.
The workaround

Reuse a region already counted in the account's history instead of requesting a new one. europe-west1 had been used before, and does support domain mapping.

08c · The MongoDB mystery in europe-west1

The new service deployed cleanly, but every page needing the database failed:

MongoServerSelectionError: connection <monitor> to <ip>:27017 closed
MongooseError: Operation `issues.find()` buffering timed out after 10000ms

Ruled out in order: wrong password (regenerated twice), IP not allow-listed (already open), the cluster being down (Atlas's own dashboard loaded data fine), a VPC misconfiguration (none existed), a live Atlas outage (status page clear), and raw reachability (a Cloud Shell TCP test reached all three database servers directly; MongoDB Compass on a personal PC connected instantly with the same credentials).

Root causeFix
Cloud Run's default sandbox ("Gen 1") struggles to hold MongoDB's persistent connections open. Containers → General → Execution environment → Second generation
The code's own connection timeout was deliberately set to 5 seconds (tuned for Mumbai) — too tight for the extra distance to Belgium. Raised to 20 seconds in server.js 
mongoose.set('bufferTimeoutMS', 20000);
mongoose.connect(MONGO_URI, { serverSelectionTimeoutMS: 20000 });

Confirmed: the first request after the fix succeeded in 7.4s (would have failed at the old 5s cutoff); every request after that took 1.1–1.5s, same as any other region. Side-discovery: the Atlas cluster itself is hosted on Google Cloud in asia-south1 (visible in its internal hostname, mtm-gcp-ass1-...) — confirming distance was the whole story.

08d · A region tried and ruled out: asia-south2

Deployed as a comparison test — connected to the database near-instantly (confirming the distance theory), but Domain Mappings aren't available there either. Kept only as a diagnostic; safe to delete.

09
STEP 09

The password lesson

was broken

While chasing login problems, the Admin account's password got typed directly into Atlas's database viewer instead of through the app. The app always stores passwords scrambled ("hashed") — typing one in raw stores it as plain text, which can never match at login.

Rule going forward

Never edit a password field directly in Atlas's Data Explorer. Always go through the website itself — "Forgot password?", or the Admin's reset-password button next to a user in the Control Panel.

10
STEP 10

Email deliverability

not yet fixed

Password-reset and OTP emails report "sent" successfully but never arrive. Cause: SMTP_FROM is a personal @gmail.com address, and Gmail's own anti-spoofing rules don't allow a third-party sender like Brevo to convincingly send mail "as" a Gmail address — Brevo's own dashboard flags it directly as non-compliant with current Google/Yahoo/Microsoft sender requirements.

The real fix: a sending address on an owned domain (e.g. noreply@actonissues.blog), verified in Brevo — the same kind of DNS work as Step 08, worth batching next time DNS is touched.
